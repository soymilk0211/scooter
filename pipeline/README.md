# 資料管線

把政府開放資料轉成 App 內附的種子 SQLite。依序執行：

```bash
python taipei_parse.py          # 1. 下載並解析台北市待轉例外 CSV
python taipei_geocode.py        # 2. 用 OSM 路網把路口解析成座標
python import_enforcement.py    # 3. 下載科技執法與固定測速點位（自帶座標）
python build_seed.py            # 4. 組成 scooter_seed.db
cp build/scooter_seed.db ../app/src/main/assets/
```

只需要標準函式庫，無外部相依。Overpass 回應快取在 `build/cache/`，重跑不會重打 API。

## 各階段做了什麼

**taipei_parse.py** — 把三份 Big5 編碼的 CSV 正規化。核心是「方向」欄的解讀：
`A往B` 表示從 A 側來、往 B 側去，因此進入方位角是 A 的反向。`南往北` 這類對向值
只描述進入車道，左轉方向由「這是左轉規則」隱含推得。`--selftest` 會驗證這套解讀。

**taipei_geocode.py** — **一次**抓回所有相關路名的路網幾何，交叉點全在本機算。
先前每組路口打一次 API 的版本，單一查不到的路口最壞要跑近一小時。消歧義用了三層：
行政區界過濾（查詢用的矩形必然涵蓋新北，而新北也有仁愛路、中正路）、節點群聚
（分隔式大路一個路口有多個號誌節點）、以及號誌篩選（有待轉規則的必定是有號誌的
大路口）。

**import_enforcement.py** — 臺北市科技執法（自帶座標）加上全國固定測速
（[dataset 7320](https://data.gov.tw/dataset/7320)，含速限與拍攝方向）。

排除三種：純違規停車（騎乘中警示停車執法沒有意義）、國道／快速道路／高架
（白牌禁行，ADR-0006，而且它們常懸在平面道路正上方，留著會在騎士不在那條路上時響）、
區間測速（是**狀態**不是接近事件，另存 `enforcement_sections_raw.json` 待用）。

排除快速道路不能只靠關鍵字：地址常常只寫「台61線60.1公里處」。`台61`～`台88`
那個線號區塊就是快速公路系列，**臺／台兩種寫法都要吃**。「拍攝方向」有十幾種寫法，
只解析能確定終點的那幾種（`北向南`、`往南`、`南下車道`、`西南向東北`），
其餘一律當成不限方向 —— `南向` 是「往南」還是「南向北」的簡寫，資料本身沒有說。

**build_seed.py** — 只有地理編碼狀態為 `ok` 的規則會進資料庫。`suspect` 與
`failed` 一律寫進 `build/review_coords.csv` 等人工補座標，因為自動編碼錯誤會在
錯誤的路口播放錯誤的指示，那比沒有資料危險（ADR-0001）。

## 實地查核

`field_checks.json` 記錄騎士到現場看牌子得到的事實，**蓋過管線的所有推導**，
信心固定為 100。以（路口原文, 面向角度）為鍵 —— 不用路名當鍵，因為路名正是
最常出錯的欄位，拿它當鍵會自我矛盾。

存在的理由：地理編碼與臂判定都是啟發式的，改一個門檻就會牽動幾十筆，而且無法
自我驗證。實地事實不該每次重跑管線就被沖掉。

`python make_ride_list.py` 產生按風險排序的查核清單。排序依據是**錯誤的方向性**：
說「直接左轉」而現場要待轉會讓騎士吃罰單，反過來只是慢一點；再疊上規則年齡，
2009 年以前生效的最可能已經改建。影像判讀已經指出矛盾的排在最前面。

## 影像判讀

看街景照片判規則，**權威低於官方資料**。證據覆蓋順序是

    實地查核 > 官方 > 影像查核（依影像年份遞減）> 回報共識 > 觀察

所以判讀結果只用來**指出矛盾**，不改規則 —— 街景判讀的天花板在資訊本身（現場常
同時有左轉專用道箭頭與待轉標誌，照片分不出那條車道是給汽車還是機車），當矛盾
偵測器才是它的正確用法。

```bash
python make_corridor_page.py --list             # 有哪些廊道可以判
python make_corridor_page.py --all              # 全部廊道 + build/corridor_index.html 目錄頁
# 雙擊 corridor_index.html 開始判，點完按「匯出 JSON」
python apply_image_checks.py build/image_checks_內湖路一段_東.json
python build_seed.py                            # 不一致的寫進 build/image_conflicts.csv
python make_ride_list.py                        # 那些矛盾會排到查核清單最前面
```

一頁是**一條路一個方向**，路口按騎過去會遇到的順序排（投影到正方位，所以同一條路的
兩個方向剛好互為反序），每個配上朝著行進方向拍的 Mapillary 影像（新的排前面）、
經緯度與面向角度。

- **不要發布成 Artifact。** 那裡的 CSP 擋外部主機，影像載不進來。
- **影像預設內嵌**（1024 寬、每個路口三張，單頁幾 MB），所以那個 HTML 檔自己就完整：
  雙擊就能開，不必配合任何資料夾、不必起伺服器。這是踩過坑之後的預設 —— 相對路徑
  只在「從影像資料夾旁邊開」時才成立，換個開法就是一排破圖，而破圖跟「這個路口
  沒有街景」在畫面上長得一模一樣，處置卻完全相反。頁面因此會在圖載不出來時換上
  一句說明，不會只留一個空白框。
- `--files` 改用相對路徑加 2048 寬、每個路口六張：頁面只有幾十 KB、放大更清楚，
  但那個 HTML 必須跟 `build/corridor_images/` 放在一起，搭 `--serve` 最省事。
  `--link` 直接連 Mapillary（連結有期限，過幾天就變破圖）。
- `--all` 一次產完所有廊道，並附一頁 `corridor_index.html` 目錄：有影像的排前面，
  每一列的「已判」直接讀該頁的 localStorage，所以進度不必自己記。
- 判讀紀錄存在瀏覽器的 localStorage，關掉頁面不會不見；**但按過「匯出 JSON」之前，
  那些判讀只存在那一個瀏覽器裡**。
- 判讀寫進 `field_checks.json` 的 **`image_checks`**，不是 `checks`。兩個陣列在結構上
  就分開，權威差異才不會退化成一個要記得去讀的旗標。已經有實地查核的一律略過。

**Mapillary 的 `compass_angle` 不能用來篩方向。** 那是上傳裝置寫的，沒有羅盤資料時
填 0，而 0 與正北無法區分 —— 實測台北某路口的 86 張影像那一欄全部是 0。要用
`computed_compass_angle`（Mapillary 由影像重建算出來的），同一批影像 100 張都有值。

## 注意事項

`build_seed.py` 的建表語句必須與 `data/src/main/kotlin/tw/scooter/data/Schema.kt`
保持一致，`cell_of()` 必須與 `core-rules` 的 `Grid.cellOf` 位元對位元相同 ——
後者由 `GridParityTest` 把關。網格值不一致時 App 不會崩潰，只會安靜地查不到規則。
