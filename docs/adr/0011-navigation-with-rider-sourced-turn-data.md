# 做導航，而缺的那層資料由用路人建檔

ADR-0007 決定做導航，當天晚上被 ADR-0010 推翻。推翻的理由是一筆不存在的資料：
**車道級禁行機車覆蓋率 0%**（ADR-0009 實測台中 1,191 段主要幹道）。沒有那一層，
導航會跟 Google Maps 一樣把騎士導上禁行機車的車道 —— 付出與它競爭的全部成本，
卻沒有任何差異化。

**那個論證有一個錯誤的前提：它假設車道級禁行機車是路線問題。它不是。**

內側車道禁行機車**不會讓那條路變成不能走的路**。騎士照樣走那條路，只是走在外側。
它改變的是**到了路口能不能直接左轉** —— 而那正是待轉規則要回答的問題，
本專案已經有一套播報機制在處理它。

一旦把「走哪條路」與「路口怎麼轉」分開，兩層的資料狀況完全不同：

| 要遵守的規則 | 資料現況 | 由誰負責 |
| --- | --- | --- |
| 國道／快速道路／高架禁行白牌 | 結構性判定可行（ADR-0006 實測 `motor_scooter` 確實避開國道） | 路線層 |
| 禁止左轉／右轉／迴轉 | **臺北市 OSM 有 1,204 條轉向限制關聯**（2026-08-18 實測，見下） | 路線層 |
| 車道級禁行機車 | **臺北市主要幹道 1.1%，而且它不改變路線** | **不收集**，見下 |
| 待轉／直接左轉 | 官方例外 118 條 + 用路人建檔 | 轉向層，用路人建檔 |

## 車道級禁行機車也不建檔：要的是結果，不是成因

原本打算把這一層交給用路人回報。**2026-08-18 決定連收集都不做**，理由是
騎士停在路口時答不出「這條路內側車道禁不禁行機車」—— 那要看路面標線與號誌桿上
的小牌子，而他正戴著安全帽、在一個只有幾秒的空檔裡。回報太難的東西，
收到的是雜訊不是資料。

**而且不需要。** 內側車道禁行機車之所以重要，只因為它決定騎士到不到得了左轉
專用道，也就是**能不能直接左轉** —— 而那正是待轉回報直接回答的問題：

- 回報「直接左轉」＝ 他到得了左轉車道。
- 回報「待轉」＝ 他到不了，或現場要求待轉。

兩種情形對騎士的指示完全相同，成因是哪一個並不改變播報。**收結果不收成因，
問題從一個看不懂的技術問題變成一個他每天都在做的判斷。**

**2026-08-18 補充：這個決定後來找到了第二個更強的理由。** 臺北市交通局其實有
明文政策（單向三車道以上內側車道禁行機車）與配套的例外清單，也就是說車道級
在臺北是**推導得出來的**，不必量也不必問。花力氣去問一萬個騎士一個交通局已經
公告過的答案，是最糟的一種眾包。細節見 HANDOVER 第一節 1b。

代價是那份推導只在有登錄政策的縣市成立（ADR-0009），而「開放機車行駛第 3 車道」
那份例外清單目前只有 PDF。兩者都不影響待轉判定 —— 待轉回報回答的是結果。

路線層今天就做得對；轉向層今天不完整，但它的不完整是**沉默**，不是錯誤 ——
不知道就不播轉向規則，騎士回到他本來就有的預設（三車道以上待轉）。
ADR-0010 擔心的那個失敗模式（把人導上不能走的車道）發生在路線層，
而路線層不缺資料。

## 2026-08-18 實測：轉向限制在臺北是有資料的

Overpass 查臺北市境內 `type=restriction*` 關聯：

| 種類 | 筆數 |
| --- | --- |
| `no_left_turn` | 600 |
| `no_u_turn` | 126 |
| `no_right_turn` | 124 |
| `only_straight_on` | 113 |
| `only_right_turn` | 33 |
| `only_left_turn` | 14 |
| `no_straight_on` | 12 |
| `restriction:conditional`（分時段禁轉，數十種寫法） | 約 180 |
| **合計** | **1,204** |

同一範圍內的號誌節點是 4,794 個。**這不能拿來算覆蓋率** —— 分母不是「有號誌的路口」
而是「現場真的立了禁轉牌的路口」，而那個數字沒有人知道。能確定的只有一件事：
它**不是 0%**，量級與問題規模相稱，而且 Valhalla 原生就吃 OSM 的轉向限制關聯，
不需要自建任何東西。這與車道級禁行機車的處境完全不同。

兩個實作時會踩到的細節：

- **分時段禁轉的寫法沒有統一。** `@ 07:00-22:00`、`@07:00-22:00`、`@ (Mo-Fr 07:00-09:00)`、
  `@ (07:00-09:00, PH off)`、`@ 07:00-09:00,17:00-19:00` 全部出現在同一個城市裡。
  這與匯入測速資料時「拍攝方向有十幾種寫法」是同一類問題，處理方式也該一樣：
  只解析能確定語意的那幾種，其餘**當成全時段禁轉**（保守方向 —— 多繞一點路，
  不會讓騎士違規）。
- **只有 11 條關聯帶 `except=motorcycle`。** 也就是說資料裡幾乎沒有記載「這個禁轉
  對機車例外」。同樣取保守方向：禁轉就是禁轉。

## 同一天量的第二件事：車道級資料在臺北仍然等於沒有

ADR-0009 的 0% 是在**台中**量的。為了確認結論不是城市差異，同一天用臺北市範圍
（`primary|secondary|trunk`，3,550 段）重量一次：

| 標籤 | 臺北 | 台中（ADR-0009） |
| --- | --- | --- |
| `oneway` | 97.1% | 98% |
| `lanes` | 68.0% | 39% |
| `maxspeed` | 24.5% | 35% |
| `motorcycle`（路段級，且已知不可信） | 5.6% | 9% |
| `lanes:forward` | 2.4% | 6% |
| `turn:lanes` | 1.0% | 1% |
| **`motorcycle:lanes`** | **1.1%** | **0%** |

臺北的 `lanes` 覆蓋率比台中好很多（68% vs 39%），但**車道級禁行機車仍然是 1.1%** ——
嚴格說不是零，實務上不能用。結論與 ADR-0009 相同，而且現在有兩個城市的數字，
不再是單一樣本。這就是為什麼那一層必須靠建檔，也是為什麼它不能擋住路線層出貨。

## 「完全遵守交通規則」這句話，第一版做得到哪一半

需求寫的是「導航必須完全遵守交通規則」。誠實的答案是：

- **路線層可以保證**：不走國道、不走白牌禁行的快速道路與高架，遵守 OSM 已記載的
  禁止左轉／右轉／迴轉與單行道。
- **車道層保證不了**，因為那筆資料在台灣不存在，而這正是本專案要建的東西。
  第一版能做到的是**不假裝知道**：沒有建檔的路口不播轉向規則。

把這件事寫在這裡，是為了讓下一個接手的人不會以為第一版出貨等於需求達成。
**達成的條件是建檔覆蓋率，不是程式完成度。**

## Consequences

- **地址搜尋、路線計算、逐向指示、偏航重算全部回到範圍內**，ADR-0007 列的那些
  現在都要做。Valhalla 的台灣圖磚已實測 309 MB、建置 6 分 14 秒（ADR-0003），
  那筆驗證留著沒有白費。
- **語音要兩條路並存**：固定句（待轉、測速）繼續走預合成 wav，逐向指示含路名與距離
  是動態的，只能走即時 TTS。實測即時 TTS 首句延遲 2.8–3.6 秒，因此**距離路口
  五秒內的那一句話必須是預合成的**，動態語句一律排在 20 秒那一次。
- **懸浮視窗降級為次要**。自己就是導航 App 的話，警示畫的是自己的畫面。
  懸浮視窗留給「切到別的 App 時仍要警示」的情境，不再是唯一出口。
- **底圖仍然必須換掉**。CARTO 的條款不供公開免費使用（ADR-0008），這件事與導航
  無關。而且它擋的不是上架，是**公開發布** —— 把 APK 放上網路讓任何人下載
  （ADR-0015）正好就是那份條款寫明不供應的用法。
- **ADR-0010 的風險評估翻轉了**：它擔心外掛難吸引使用者，而規模化只能靠被動觀察。
  導航 App 有理由讓人開著它騎完整趟路，那正是收集軌跡與建檔的前提。
- 沒有堵死回頭路。ADR-0010 的論證與這裡的反駁都在，哪天車道級資料仍然收不到，
  收回成外掛的路徑完整保留。
