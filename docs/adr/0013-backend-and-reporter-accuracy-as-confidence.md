# 有後端了：回報即時上傳，以回報者正確率作為信心指標

ADR-0008 決定沒有後端，每月固定成本 NT$0，只留「被動觀察的接收端點」當唯一例外。
現在資料建檔**整個**移交給用路人（不再有人工建檔），那個例外變成主線：
沒有一個收得到資料的地方，就沒有資料。

## 資料流

回報**按下當下立即送出**，不等任何確認畫面。理由是它要在騎士停紅燈的那幾秒內完成，
而確認畫面會把一個一秒的動作變成三秒的動作，於是他不做了。按錯的成本由共識吸收。

「立即」指的是**排隊立即，網路盡快**。回報先寫進本機 `observations`
（該表本來就有 `uploaded_at` 欄位，就是為了離線排隊而存在），
再由上傳器批次送出。**不做每筆一次連線**：機車騎乘中網路不穩，
而且逐筆連線在隧道與地下道會把電池吃光。

## 「人多就會趨於正確」在第一天不成立

這是整個模型唯一的破口。共識需要人數，而人數要靠已經有用的 App 才長得出來。
因此信心不能只看票數，要看**是誰投的**：

1. **每個裝置有一個匿名 ID**，不綁帳號、不收廣告 ID 與 IMEI。
2. **新裝置的前幾筆一律進審核佇列**（建議：前 5 筆或前 3 個不同路口，以先到者為準），
   由專案維護者親自看過。這是使用者明確要求的做法。
3. **官方開放資料的 118 條臺北市規則留著當校準基準**，不對騎士播報、不進顯示規則。
   它唯一的用途是：有人在這 118 個路口回報時，系統立刻知道他對不對，
   **正確率自動算得出來，不必人工看**。這讓需要親自審核的量少一個數量級。
4. 正確率過門檻的裝置，之後的回報不再進佇列，直接計入共識。

**正確率用 Wilson 分數下界，不用裸比例。** 第一筆答對就是 100%，
裸比例會讓一個亂按而剛好猜中的人立刻升級成可信裝置；下界會把樣本數少
這件事算進去，答對 1/1 的分數低於答對 20/20。這是冷啟動階段唯一擋得住
單人刷票的東西。

**同一裝置在同一路口同一進入方位角只算一票，取最新的那筆。**
沒有這條，一個人按二十下就能定案一個路口。

## 成本

一筆回報連同路口片段（ADR-0014）是數百位元組。100 位活躍騎士、每人每天經過
20 個路口，一天約 2,000 筆、不到 1 MB。這在 Cloudflare Workers + D1 或
Supabase 的免費層裡是雜訊等級的用量，ADR-0008 的 NT$600 上限在可預見的規模內
仍然成立。真正的成本風險不是流量，是**審核的人時**。

## Consequences

- **需要一個審核介面**，不是一個 SQL 查詢。前幾筆全部要人看，而看的人騎車、
  上班、也會累 —— 介面難用等於資料流會塞住，而塞住的時候使用者感覺不到，
  只會覺得 App 沒變聰明。
- **ADR-0008 的「每月 NT$0」不再成立**，改成「免費層內，有上限，超過就要決定
  收費或關閉」。離線包、靜態發布、山區可用那幾項不受影響 —— 上傳失敗只是延後，
  不影響騎乘。
- **信用分數（CONTEXT.md）從概念變成必須落地的欄位**，且它在伺服器端。
  守法分數仍然不落地（ADR-0005），兩者不要因為都叫「分數」就放進同一張表。
- **審核結果要能回頭改分數**。維護者判定一筆回報是錯的，該裝置的正確率必須跟著降，
  否則審核只是把錯資料擋在門口，沒有告訴系統誰在製造它。
- **「進資料庫」與「發布給其他人」是兩件事。** 回報即時上傳、即時入庫（使用者要求的
  「按下當下立即回報」講的是這一段），但只有通過審核或達到共識門檻的規則才會下發到
  別人的裝置。第一個公開版本就帶下行通道（ADR-0015），所以這道閘門**必須在發布前
  就完成**，不能等有人回報了再補。
